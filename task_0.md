# Инкремент 0 — хронологический порядок дней в календаре

## Контекст

Backend возвращает слоты в хронологическом порядке на 14 дней. Frontend группирует их
по локальному календарному дню через `Date.toDateString()`, после чего сортирует ключи
через `localeCompare` в `frontend/src/pages/guest/SlotsCalendarPage.tsx`.

Ключ имеет вид `Fri Sep 04 2026`, поэтому фактически сортируется название дня недели.
На публичном приложении 3 сентября 2026 года порядок начинался так:

```text
Fri 4 Sept → Fri 11 Sept → Mon 7 Sept → Mon 14 Sept → ... → Thu 3 Sept
```

Из-за этого первым отображалось «завтра», хотя слоты текущего и остальных дней были в
ответе API. Такой же алгоритм находится в актуальном `main`; простой redeploy проблему
не исправит.

## Цель

Группы дней всегда отображаются в возрастающем хронологическом порядке в локальной
таймзоне браузера. Первая группа должна содержать самый ранний доступный слот.

## Границы задачи

Входит:

- исправление `groupSlotsByDay` и структуры `DayGroup`;
- стабильный хронологический ключ/значение сортировки;
- E2E-регрессия на порядок дней;
- при необходимости небольшая семантическая разметка групп для устойчивого теста;
- обновление описания сценариев E2E.

Не входит:

- изменение backend, TypeSpec или 14-дневного окна;
- ограничение рабочих часов;
- новый дизайн выбора дня — это инкремент 1;
- исправление Railway-деплоя.

## Рекомендуемая реализация

1. Сохранить группировку по локальному календарному дню: именно так даты видит
   пользователь. Не группировать по обрезанной UTC-строке `startsAt`, иначе около полуночи
   слот может попасть не в тот локальный день.
2. Вместе с `key`, `label` и `slots` хранить числовое значение сортировки. Его можно
   получить из времени первого слота группы, поскольку входные слоты уже упорядочены;
   безопаснее всё равно вычислять минимум по группе.
3. Сортировать группы численно по этому значению. Слоты внутри каждой группы продолжать
   сортировать по `startsAt`.
4. Не пытаться разобрать обратно строку `toDateString()` и не сравнивать локализованный
   `label`: оба варианта зависят от браузера и locale.
5. Для E2E предпочтительно добавить группе нейтральный атрибут наподобие
   `data-day-start` с ISO-временем первого слота. Тест должен проверить, что значения
   возрастают и что первый день содержит самый ранний слот из перехваченного API-ответа.

## Тесты

Добавить отдельный сценарий в `e2e/tests/booking.spec.ts`:

1. создать тип встречи через owner UI;
2. открыть его как гость и перехватить ответ slots API;
3. получить отображаемые группы дней в DOM;
4. проверить строго возрастающий порядок групп;
5. проверить соответствие первой группы локальному дню самого раннего API-слота;
6. выбрать слот первой группы и убедиться, что форма бронирования открывается.

Тест не должен фиксировать конкретную календарную дату, язык браузера или UTC offset.
Обновить `e2e/SCENARIOS.md`, добавив сценарий и связь с FR-4.

## Проверка

```bash
cd frontend
npm ci
npm run build

cd ../e2e
npm ci
E2E_PYTHON=../backend/.venv/bin/python npm test
```

Если backend virtualenv находится в другом месте, передать его абсолютный путь через
`E2E_PYTHON`. После push должны пройти `build`, `api-tests`, `e2e` и оба запуска
`production-container`.

## Критерии приёмки

- текущий день, если в нём есть доступные слоты, расположен перед завтрашним;
- все группы дней идут хронологически независимо от locale и дня недели;
- времена внутри каждой группы также возрастают;
- основной сценарий бронирования продолжает работать;
- добавленный тест падает на прежней реализации с `a.key.localeCompare(b.key)`;
- diff не содержит изменений API или backend.
