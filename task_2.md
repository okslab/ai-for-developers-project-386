# Инкремент 2 — компактный выбор дня

## Предпосылка

Инкременты 0–1 слиты в `main`. Для UI эта задача технически зависит только от
инкремента 0: группы слотов уже имеют устойчивый хронологический порядок. Не дублировать
и не переписывать его сортировку без необходимости.

## Проблема

Backend намеренно формирует сетку круглосуточно с шагом 30 минут. Для 30-минутного типа
встречи это до 48 кнопок в день и примерно 672 кнопки за 14 дней. Все группы сейчас
отрисовываются одной длинной страницей. Даже после исправления сортировки следующий день
оказывается на несколько экранов ниже.

Рабочие часы нельзя вводить в рамках этой задачи: `spec.md` относит их к out-of-scope.
Нужно улучшить представление тех же данных, не урезая доступность.

## Цель

Показать компактную навигацию по доступным дням и одновременно отображать временные
слоты только выбранного дня. По умолчанию выбирается первый доступный день.

## Ожидаемое поведение

- над временными слотами расположен список/лента кнопок доступных дней;
- дни идут хронологически и используют существующий локальный формат даты;
- первая доступная дата выбрана автоматически;
- в DOM как доступный для взаимодействия набор отображаются слоты только выбранного дня;
- выбранный день обозначен визуально и через `aria-pressed` или эквивалентную семантику;
- переключение дня сбрасывает ранее выбранный временной слот и форму гостя;
- после конфликта и refetch текущий день сохраняется, если на нём остались слоты;
- если выбранный день исчез после refetch, выбирается первая оставшаяся дата;
- если слотов больше нет, сохраняется существующее пустое состояние;
- мобильная версия не создаёт горизонтальный overflow всей страницы: допустима отдельная
  прокручиваемая лента дат или перенос кнопок.

## Границы задачи

Основные файлы:

- `frontend/src/pages/guest/SlotsCalendarPage.tsx`;
- существующие UI-компоненты в `frontend/src/components/ui/`;
- `e2e/tests/booking.spec.ts`;
- `e2e/SCENARIOS.md`;
- `spec.md` — уточнить только способ просмотра 14-дневной доступности, не API-правила.

Не изменять contract/backend. Не добавлять календарную библиотеку ради 14 кнопок, если
задача решается текущими React-компонентами и `Intl.DateTimeFormat`.

## Состояние React

Рекомендуемая модель:

1. `dayGroups` остаётся вычисляемым значением из ответа API.
2. `selectedDayKey` хранится отдельно от `selectedSlot`.
3. Эффект синхронизации после загрузки/refetch:
   - ничего не делает, если текущий ключ ещё существует;
   - выбирает ключ первой группы, если текущего больше нет;
   - устанавливает `null`, если групп нет.
4. Обработчик смены дня очищает `selectedSlot` и `bookingError`, чтобы форма не ссылалась
   на скрытый слот другого дня.
5. Не хранить целую `DayGroup` в state: после refetch объект устареет.

## E2E-покрытие

Добавить сценарий, который:

1. создаёт тип встречи;
2. открывает календарь и проверяет, что выбран первый доступный день;
3. проверяет, что видна одна группа временных слотов, а не слоты всех 14 дней;
4. переключается на следующую дату и проверяет смену набора времени;
5. выбирает время, затем переключает день и убеждается, что форма закрылась;
6. выбирает слот на новом дне и завершает бронирование.

Адаптировать существующие helpers `selectSlot`/`selectExactSlot`: они не должны считать,
что все дни одновременно видимы. Сценарии конфликтов между типами встреч обязаны остаться
зелёными.

## Проверка

```bash
cd frontend
npm run build

cd ../e2e
E2E_PYTHON=../backend/.venv/bin/python npm test
```

Дополнительно вручную проверить desktop и узкий viewport: первая дата, последняя дата,
переключение даты после выбранного времени и пустой ответ API.

## Критерии приёмки

- пользователь может выбрать любой доступный день 14-дневного окна;
- интерфейс не выводит одновременно сотни временных кнопок;
- порядок дней из инкремента 0 сохранён;
- клавиатурная навигация и понятное accessible name доступны для кнопок дат;
- все прежние E2E-сценарии, включая оба конфликта, проходят;
- contract и backend не изменены.
