# План следующих инкрементов

План появился после проверки публичного приложения 3 сентября 2026 года. API отдавал
слоты на все 14 дней, но frontend показывал первым следующий день из-за сортировки
локализованных строк дат. Одновременно публичный Railway-контейнер обслуживал старую
схему маршрутов (`/event-types` вместо актуального `/api/event-types`), то есть его
ревизию нельзя было надёжно сопоставить с `main`.

Инкременты выполняются строго по порядку. Каждый инкремент начинается от актуального
`origin/main`, выполняется в отдельной ветке `codex/…`, оформляется одним тематическим
Conventional Commit и отдельным PR. После каждого инкремента приложение и все CI-проверки
должны оставаться рабочими.

- [ ] **Инкремент 0 — хронологический порядок дней в календаре.** Исправить сортировку
  групп слотов и добавить браузерную защиту от регрессии. Детали: [task_0.md](task_0.md).
- [ ] **Инкремент 1 — идентификация запущенной ревизии.** Контрактно добавить read-only
  health/deployment endpoint и передавать в контейнер Git SHA сборки. Детали:
  [task_1.md](task_1.md).
- [ ] **Инкремент 2 — проверка публичного Railway-деплоя.** Автоматически убеждаться,
  что production отвечает актуальным API-префиксом и запущен из ожидаемого коммита
  `main`. Детали: [task_2.md](task_2.md).
- [ ] **Инкремент 3 — компактный выбор дня.** Вместо вывода сотен кнопок одновременно
  показывать навигацию по доступным дням и слоты выбранного дня. Детали:
  [task_3.md](task_3.md).

## Общие правила завершения инкремента

1. Не начинать следующий инкремент до слияния предыдущего в `main`.
2. Не менять `.github/workflows/hexlet-check.yml` и `.github/workflows/README.md`.
3. При изменении API сначала менять TypeSpec, затем регенерировать OpenAPI и типы клиента.
4. Не подменять продуктовые требования рабочими часами: в текущем `spec.md` ограничения
   business hours явно находятся вне scope.
5. Обновлять checkbox этого файла только вместе с реально завершённым инкрементом.
6. Перед PR запускать проверки, перечисленные в соответствующем `task_i.md`, и дождаться
   зелёных GitHub Actions после push.
